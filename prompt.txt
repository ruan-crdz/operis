# 9. JUSTIFICATIVA TÉCNICA DA PALETA

Não use “psicologia das cores” pseudocientífica.

A justificativa deve ser objetiva.

A combinação foi escolhida para proporcionar:

1. diferenciação em relação ao padrão branco/azul predominante em software corporativo;
2. contraste alto;
3. hierarquia visual;
4. menor aparência de template genérico;
5. diferenciação clara de IA usando violeta;
6. diferenciação semântica de sucesso, atenção e erro.

Contrastes previamente calculados:

```text
#161A17 em #F3EFE6 = aproximadamente 15.32:1

#4D554F em #F3EFE6 = aproximadamente 6.71:1

#2C6E5B em #FBF8F1 = aproximadamente 5.68:1

#FBF8F1 em #2C6E5B = aproximadamente 5.68:1

#7A817B contra #FBF8F1 = aproximadamente 3.77:1

#5A3DAA em #FBF8F1 = aproximadamente 7.38:1

#6C4B00 em #FFF1C2 = aproximadamente 7.04:1

#8F2D24 em #FCE8E6 = aproximadamente 6.94:1
```

WCAG 2.2 AA exige aproximadamente:

```text
texto normal        >= 4.5:1
texto grande        >= 3:1
componentes críticos não textuais >= 3:1
```

Todos os componentes devem manter conformidade WCAG 2.2 AA.

Sempre que você introduzir uma nova combinação de cor, confira contraste.

Cor nunca pode ser a única indicação de estado.

Exemplo errado:

“vermelho significa erro”.

Exemplo correto:

ícone + texto “Erro” + cor.

* salário;
* INSS;
* FGTS;
* IR;
* férias;
* impostos;
* lançamentos contábeis definitivos;
* obrigações;
* valor financeiro final.

* identificar colunas;

* classificar documentos;
* detectar possíveis anomalias;
* resumir diferenças;
* explicar erros;
* gerar checklist;
* auxiliar pesquisas;
* sugerir próximos passos.

Fluxo:

```text
AI suggestion
→ confidence
→ evidence/reason
→ human review
→ approval
→ deterministic execution
```

Sempre registrar quando IA participou de uma decisão.

Apresente no timezone adequado do usuário.

Default inicial:

`America/Sao_Paulo`.

# 31. VALORES MONETÁRIOS

Isto é CRÍTICO.

Nunca utilize floating-point JavaScript para cálculos financeiros sérios.

Não faça:

```ts
0.1 + 0.2
```

como fundamento de cálculo monetário.

PostgreSQL:

utilize `numeric`.

TypeScript:

utilize `decimal.js` quando houver cálculos.

Crie abstrações de domínio.

Rounding deve ser explícito.

Quando no futuro implementarmos folha e impostos, cada regra deverá definir:

* precisão intermediária;
* regra de arredondamento;
* precisão final.

# 137. FONTES E PRINCÍPIOS QUE FUNDAMENTAM ESTAS DECISÕES

Considere durante implementação:

**W3C — WCAG 2.2**

Referência normativa para contraste, foco, navegação por teclado, dragging, targets e acessibilidade.

**Radix UI — Accessibility**

Primitives alinhados com padrões WAI-ARIA, keyboard navigation e focus management.

**Supabase — Row Level Security**

RLS deve proteger toda tabela exposta e ser testada. `service_role` bypassa RLS e deve permanecer server-side.

**Supabase — Edge Functions**

Adequadas para endpoints e orquestração; operações longas/pesadas devem ir para workers/background execution.

**OpenAI — Responses API**

Interface moderna para integração com modelos.

**OpenAI — Structured Outputs**

Utilizar JSON Schema para saídas estruturadas em vez de parsing frágil de texto.

**Geist Design System — Typography**

Tabular numerals são indicados para apresentação consistente de números.

**Bigelow, 2019 — Typeface Features and Legibility Research**

Tipografia digital e características das fontes afetam legibilidade; decisões não devem se apoiar apenas em serif/sans-serif como regra universal.

**Sheedy et al. — Text Legibility and the Letter Superiority Effect**

Fonte, tamanho, largura dos traços e parâmetros de display afetam legibilidade.

**Dobres, Chahine & Reimer — Effects of ambient illumination, contrast polarity, and letter size on text legibility**

Evidências de vantagem de polaridade positiva em determinadas condições sustentam um tema claro como default de aplicação altamente informacional, mantendo dark mode como opção.

**Humar et al. — The impact of color combinations on the legibility of text presented on LCDs**

Combinação de cores e contraste afetam legibilidade.

**Tractinsky et al. — What is beautiful is usable**

Estética pode afetar percepção de sistemas.

**Tuch et al. — Is beautiful really usable?**

A relação entre estética e usabilidade é mais complexa do que uma regra simples; boa usabilidade deve ser realmente implementada e validada.
